# 007 — Grid-based spatial index for nearby-node searches, cached per OsmData instance

## Context
`FindNearByRadius`, `FindNearestNode`, and `FindNearbyNodes` on `OsmEntityFinder` all do an identical linear scan over `data.Nodes`, computing a Haversine distance per node. Tracked as issue #2: for all of Norway, a single `FindNearByRadius` call reportedly takes 144 minutes and 32 GB.

`OsmEntityFinder` is registered Transient (`AddOsmToolkit()`) and holds no state of its own - `OsmData` is passed as a parameter to every call. This is the same shape that made ADR-004's in-flight-fetch tracking non-trivial: a Transient service can't cache anything in an instance field, since it's recreated on every DI resolution. The only thing actually shared across repeated finder calls is the caller-supplied `OsmData` itself.

## Decision
A grid-based spatial index over `data.Nodes` is built lazily and cached in a `ConditionalWeakTable<OsmData, GridNodeIndex>` scoped to `OsmEntityFinder`, using the same thread-safe `GetValue(key, factory)` pattern ADR-004 already established for coalescing in-flight Overpass fetches. The first spatial-finder call against a given `OsmData` instance builds the index; every later call against that same instance reuses it. This required no interface or method-signature changes - `FindNearByRadius`, `FindNearestNode`, and `FindNearbyNodes` keep their existing public shape, so the change is entirely internal and carries no breaking-change risk.

All three linear-scan methods are backed by the same index, not just `FindNearByRadius` - leaving `FindNearestNode`/`FindNearbyNodes` on linear scan next to a documented indexed `FindNearByRadius` would be the same kind of inconsistency issue #7's design deliberately avoided (fixing part of a bug class and leaving the rest).

The index is a uniform grid over latitude/longitude, with cell size specified in meters and corrected for longitude's latitude-dependent shrinkage (reusing the same `Math.Cos(latitude)` approach `OsmEntityFinder.EstimateAreaSquareKilometers`/`CalculateCoordinatesToMeters` already use). No new package dependency is introduced.

**Tag-filtered calls are explicitly not indexed.** `FindNearbyNodes(..., tags)` calls `FindByTags` first, which returns a brand-new `OsmData` via `new OsmData(data.Header, data.Bounds, foundNodes, foundWays, foundRelations)` - an instance that is used exactly once and then discarded. Keying the index cache by instance identity gives that throwaway object nothing but index-build overhead, no reuse. Tag-filtered calls keep today's behavior: filter first (typically to a much smaller subset), then linear-scan that subset - which is normally already fast, since it's small.

## Alternatives considered
- **R-tree instead of a grid**: rejected for now. An R-tree adapts to OSM's highly non-uniform density (dense cities, empty wilderness) better than a fixed grid, and is the standard tool for this exact problem - but this project has no geospatial dependency today, so it would mean either a new third-party package (its own lock-in decision) or a substantial hand-rolled implementation. A grid is a smaller, reversible first step; nothing here prevents swapping the index structure later, since it's entirely internal to `OsmEntityFinder`.
- **An explicit opt-in method the caller calls to build the index first**: rejected - new public surface to design and document, and silently does nothing if a caller forgets to call it. The lazy, automatic approach matches how `IOsmDataSource`'s own cache is already fully transparent to callers.
- **Restructuring tag-filtered searches to use the index too** (search the full dataset via the index first, filter by tag afterward): rejected - reorders `FindNearbyNodes`'s filter-then-search into search-then-filter, which changes its semantics for the limit+tags case (e.g. "5 nearest matching a tag" would need an expanding-radius search instead of a single pass). A meaningfully bigger, riskier change than this issue's stated goal.
- **Restructuring `OverpassOsmDataSource.CloneForCaller` to stop cloning, so cache hits could share one stable `OsmData` instance and the index would survive across independent fetches too**: rejected - that clone exists specifically because a prior code review found the cache handing out its own live instance let a caller's mutation corrupt the shared cached entry for every future caller (`Node`/`Way`/`Relation` remain mutable via `OsmEntity`'s public setters). Reverting it reopens that bug to fix this one. Tracked as its own issue (#18), since the real fix - genuine `OsmData`/`OsmEntity` immutability - is a breaking change to a published public API.

## Consequences
The index only helps within a single fetched `OsmData` instance's lifetime - e.g. one request that fetches data once and runs several finder calls against that same local variable. It does not help across two independent top-level fetches of the same logical data, including two `IOsmDataSource.GetOsmDataAsync` calls for the identical bounding box, even when one is served from that data source's own network-level cache (see #18: `CloneForCaller` hands back a fresh `OsmData` instance on every call, cache hit or not). Tag-filtered `FindNearbyNodes` calls also do not benefit, for the same instance-identity reason, and keep their current linear-scan cost.
