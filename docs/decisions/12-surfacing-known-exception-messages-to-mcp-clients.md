# 012 — Surfacing known exception messages to MCP clients via McpException

## Context
ADR-11 wrapped Overpass/HTTP fetch failures in `OsmDataUnavailableException` specifically so a client would see "a clean, readable error message... instead of a raw exception dump," and assumed "the MCP SDK's existing unhandled-exception-to-`IsError`-result behavior... does the rest; no new transport-level handling was needed."

That assumption was never checked against a real MCP client until this was done while capturing real example output for the project's README - a documentation pass, not a bug report. Dumping the raw `CallToolResult` JSON from a real stdio session (not just the client library's display of it) showed the SDK's default behavior replaces *any* thrown exception - regardless of type or message - with a generic `An error occurred invoking 'find_near_point'.` and nothing else. Neither `PlaceNotFoundException`'s message (`No place found matching "X".`) nor `OsmDataUnavailableException`'s message reached the client at all. The same session also found that `find_near_point`'s optional `tags` parameter had no C# default value, so a caller that omitted the key entirely - exactly what the tool's own description invites ("Omit to match any node") - hit the same generic failure instead of matching any node.

## Decision
`McpErrorTranslator.TranslateKnownFailuresAsync<T>` (`OsmToolkit.Mcp/Tools/McpErrorTranslator.cs`) catches only `PlaceNotFoundException` and `OsmDataUnavailableException` and rethrows them as `ModelContextProtocol.McpException(ex.Message, ex)` - a type whose message the SDK does forward to the client as-is. Every other exception type is left to propagate untouched, so it still falls through to the SDK's generic, detail-free fallback rather than risking an unanticipated internal exception leaking detail to a remote client.

All three `[McpServerTool]` methods (`FindNearPointTool`, `SearchByTagsInAreaTool`, `RouteBetweenPointsTool`) route their existing one-line delegation to the handler through this translator, rather than calling the handler directly. This keeps the Tool classes' documented shape - "transport/attribute plumbing only, with no logic of its own" - intact: the translation is protocol-shape plumbing (which exception types the wire format is allowed to describe), not business logic.

`FindNearPointTool.FindNearPoint`'s `tags` parameter was also reordered to sit right before `cancellationToken` and given `= null`; `cancellationToken` was given `= default` in turn, since C# requires every parameter after the first optional one to also be optional. Tool arguments are bound by name from the client's JSON, not by C# parameter position, so this reordering has no effect on how a client calls the tool.

## Alternatives considered
- **Making `OsmDataUnavailableException` derive from `McpException` directly**, removing the need to translate it: rejected for consistency - `PlaceNotFoundException` lives in the core `OsmToolkit` library and cannot depend on the MCP SDK's `McpException` without leaking a transport-specific dependency into a library also used by non-MCP consumers. Since one of the two exceptions must be translated at the boundary regardless, both are handled the same way at the same boundary instead of running two different mechanisms for the same problem.
- **Translating in the handler layer instead of the Tool layer**: rejected - handlers are deliberately transport-agnostic (each one's own doc comment: "can be constructed and called directly in a test, without any MCP-specific transport or attribute involved"). `McpException` is an MCP SDK type; introducing it there would leak a transport concern into a layer designed not to have one.
- **A blanket catch-all that forwards every exception's `Message` to the client**: rejected as a security regression, not a fix. It would forward whatever text an unanticipated internal exception happens to carry - the whole point of the SDK's generic default - to a remote, arbitrary MCP client. Only the two exception types `OsmToolkit.Mcp` deliberately designed with client-safe messages are translated; anything not explicitly added to the filter keeps today's generic fallback.

## Consequences
A client calling any of the three tools now sees the specific message ADR-11 already intended - `No place found matching "X".` or the Overpass-fetch-failure message - instead of a generic, detail-free error. `find_near_point`'s `tags` parameter can now actually be omitted, matching its own description, instead of only accepting an explicit `null`.

Any future MCP tool or new exception type that should be client-safe must be added explicitly to `McpErrorTranslator`'s catch filter; a genuinely new, unanticipated exception type stays behind the SDK's generic message until someone deliberately decides its text is safe to show a remote client. This is the same "measure the actual thing, don't trust the design" discipline ADR-08 and ADR-09 already established for performance, applied here to a correctness/UX claim instead of a latency number.
